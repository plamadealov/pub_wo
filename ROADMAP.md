# Дальнейшие шаги: CAPM / VaR / ES + новости

Учебный проект в этой папке. Секреты только в `.env` (не коммитить).

---

## Фаза 0 — Зафиксировать контракт API (0.5–1 день) ✅ сделано


- Описать JSON-схемы:
  - **запрос** портфеля: список `{ ticker, weight | notional }`, окно истории (дней), уровни α для VaR/ES, идентификатор рыночного индекса (например IMOEX).
  - **ответ**: веса, портфельная β, per-ticker β, исторический 1d VaR_α, ES_α, метаданные (число наблюдений, даты, валюта).
- Зафиксировать **знак потерь** (удобно: отрицательная доходность = убыток) и единицы (доли / проценты в ответе).
- Эндпоинты-черновик: `POST /api/portfolio/analyze`, `GET /api/instruments/resolve?ticker=...` (опционально).

**Критерий готовности:** фронт может работать против «мок-ответа» без реальных котировок.

Реализация: `POST /api/portfolio/analyze`, `GET /api/instruments/resolve`, схемы в `backend/app/schemas/portfolio.py`, mock в `backend/app/services/mock_analyze.py`, кнопка на фронте; тесты `backend/tests/test_phase0.py`.

## Фаза 1 — Рыночные данные (MOEX ISS) (2–4 дня) ✅ сделано


- Клиент `httpx`: загрузка дневных рядов для тикеров и индекса (кэш в SQLite внутри проекта, например `data/cache.sqlite`).
- Нормализация: общий календарь торговых дней, выравнивание пропусков, лог-доходности (или простые — единообразно).
- Конфиг: `MOEX_ISS_USER_AGENT` из env (требование площадки).
- Обработка ошибок: нет истории, делистинг, слишком короткий ряд → понятные поля в ответе API.

**Критерий:** по фиксированному списку тикеров бэкенд стабильно отдаёт сшитую матрицу доходностей за 1–2 года.

Реализация: `app/moex/client.py`, `app/moex/cache.py`, `app/services/market_data.py`, кэш `data/moex_cache.sqlite`.

## Фаза 2 — Аналитическое ядро (2–4 дня) ✅ сделано


- **β:** OLS (numpy или statsmodels) актива к рынку на склейке рядов; портфельная β = Σ w_i β_i.
- **VaR / ES (исторические):** по распределению **портфельной** дневной доходности; ES = среднее по α-хвосте (в терминологии проекта «пробой» = ES).
- Опционально: **Rf**, **E(Rm)** и ожидаемая доходность по CAPM — как отдельные поля, с явным указанием источника/сценария.
- Юнит-тесты на синтетических рядах (известные квантили).

**Критерий:** совпадение с ручным расчётом в ноутбуке на маленьком примере.

Реализация: `app/services/analytics.py`, `app/services/analyze_pipeline.py`, тесты `tests/test_analytics.py`.

## Фаза 3 — Фронтенд: портфель и метрики (3–5 дней) ✅ сделано

**Критерий:** полный цикл «собрал портфель → увидел метрики» без новостей.

Реализация: `frontend/src/App.tsx` (таблица позиций, параметры, **Recharts** по полю `chart`), чекбокс **Mock**.

## Фаза 4 — Новости (2–3 дня)

- Абстракция `NewsProvider` (интерфейс + одна реализация): запрос по тикеру/ключевому слову, фильтр **≤ 24 ч**.
- Ключи только из env (`NEWS_API_KEY` и т.д.).
- Эндпоинт `GET /api/news?tickers=A,B,C` или включение в ответ анализа.
- UI: лента **по портфелю** и **по выбранному тикеру**.

**Критерий:** для 2–3 ликвидных тикеров стабильно видны заголовки за сутки (или осмысленный fallback при отсутствии API).
